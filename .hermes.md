# Hermes project rules — sleeper-zone-desktop

Hermes: when working in this repo, adopt this behavior. `AGENTS.md` (repo
root) is the operating manual — commands, layout, invariants, boundaries.
This file adds Hermes-specific conduct; do not duplicate it, layer on it.

## Session behavior

- Read `AGENTS.md` before your first code edit in a session. Build/test
  commands live there and are verified — do not re-derive them.
- Before starting new work, check `ROADMAP.md` and the approved spec for
  the current milestone in `docs/superpowers/specs/` (when they exist).
  Build the milestone's items, not whatever seems interesting.
- Boundary discipline (AGENTS.md §Non-negotiable): correctness before
  speed, no unjustified `unsafe`, parity tests guard behavior. Decline
  requests that violate these with a pointer to the rule unless the user
  overrides explicitly.

## Skill routing (Hermes skills — load with skill_view before the task)

Run Hermes for this repo via the repo-root **`./dev`** script — the
primary entrypoint for development here. It is idempotent: it creates the
**sleeper profile** (`hermes --profile sleeper`), prunes irrelevant skills
from that profile via `skills.disabled`, bootstraps the repo-local project
skills in `.hermes/skills/`, and ensures the repo is trusted — then drops
you into a session. Subcommands: `./dev setup` (bootstrap only),
`./dev doctor` (verify environment), `./dev -q "prompt"` (one-shot; all
other args pass through to hermes). The default profile keeps the full
catalog for everything else.

| Task in this repo | Load skill |
|---|---|
| Writing or reviewing Rust code | `rust` — modern Rust conventions for this repo |
| Writing any new feature or fix | `test-driven-development` — parity tests first |
| A bug that isn't immediately obvious | `systematic-debugging` — root-cause before fixing |
| Before committing code changes | `requesting-code-review` — mandatory for multi-file changes |
| Messy milestone chunk just landed | `simplify-code` — run after each milestone |
| Validating an unknown design before building | `spike` — throwaway experiment first |
| Executing an approved plan (multi-task) | `subagent-driven-development` |
| Plan interview before implementation | `grill-me` — invoked by the user |
| "How big is the codebase" metrics | `codebase-inspection` |
| PRs, issues, reviews on the GitHub repo | `github` |
| Substantial autonomous/multi-step work | `unlazy` — keep working to verified done |
| Hermes config/theming questions | `hermes-agent` |
| Bash scripts in this repo | `shell-portability` |

Negative controls — do NOT load a skill for a near-neighbor ask:

- An ordinary reproducible bug ≠ `spike`; spike is for validating an
  unknown *design* before building, not debugging.
- A failing test in existing code ≠ `test-driven-development` from
  scratch; reproduce, then `systematic-debugging`.
- A micro-optimization inside an existing function ≠ `rust` review; run
  the benchmark, don't restyle code.
- Idle "how big are we" ≠ a full `codebase-inspection` run unless metrics
  were actually requested.
- Doc/comment wording tweaks load no skill at all.

## Hooks (sleeper profile)

Configured in `~/.hermes/profiles/sleeper/config.yaml`, scripts in
`~/.hermes/agent-hooks/`:

- `sleeper-git-guard.sh` — pre_tool_call on `terminal|execute_code`,
  fail_closed: blocks mutating git (push/pull/commit/merge/...); read-only
  git passes. Commit through the user or with explicit approval.
- `sleeper-formatter.sh` — post_tool_call on `write_file|patch`: runs
  `cargo fmt` on edited `.rs` files when a `Cargo.toml` sits above them.
  Guarded no-op until the Rust toolchain and crate exist.
- `sleeper-evidence.sh` — post_tool_call on `terminal`: appends a compact
  JSONL line per command to `~/.hermes/agent-hooks/sleeper-evidence.jsonl`.
- `sleeper-inject-git-status.sh` — pre_llm_call: injects branch + dirty
  file status when the session cwd is inside this repo.

First session start may prompt for per-profile hook allowlist consent, or
run `hermes --profile sleeper --accept-hooks` once.

## Engineering gates (do these yourself, unprompted)

- Every change: `cargo fmt --check && cargo clippy --all-targets -- -D
  warnings && cargo test` must be green before declaring done.
- Every `perf:` claim needs a `cargo bench` before/after number.
- Never commit secrets, `.env*`, or `target/`.
